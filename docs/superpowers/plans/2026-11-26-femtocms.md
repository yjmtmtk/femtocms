# femtocms Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `npx femtocms init` の1コマンドで利用者の Cloudflare に立ち上がる、管理画面のない CMS（操作は MCP・CLI・HTTP API）を作り、npm と GitHub で公開できる状態にする。

**Architecture:** Worker 1本（Hono）に HTTP API・MCP（Streamable HTTP, stateless）・画像配信・embed.js・プレビューを載せ、D1 と R2 に保存する。権限チェックと検証を含むすべての操作は `worker/src/core/` の関数（＝操作層）にあり、HTTP ルートと MCP ツールはそれを呼ぶだけ。CLI は HTTP API を呼ぶ。導入系コマンドは同梱の wrangler を子プロセスで呼ぶ。

**Tech Stack:** TypeScript, Hono 4, zod 4, @modelcontextprotocol/sdk 1.32（`WebStandardStreamableHTTPServerTransport` + `CfWorkerJsonSchemaValidator`）, marked, D1, R2, wrangler 4, vitest 4.1 系 + @cloudflare/vitest-pool-workers, commander, @clack/prompts, tsup, happy-dom（embed のテストのみ）。

**Spec:** `docs/superpowers/specs/2026-11-26-femtocms-design.md`（実装者は必ず併読すること。本計画は spec の章番号を「spec §7」のように参照する）

## Global Constraints

- パッケージ名 `femtocms`、bin 名 `femtocms`、Worker 名の初期値 `femtocms`。ローカルのフォルダ名 `nanocms` はどこにも出さない。
- Node.js 20 以上（`"engines": { "node": ">=20" }`）。
- Cloudflare 無料枠で動くこと。Cloudflare Images・有料機能に依存しない。
- 管理キーの接頭辞 `fcms_admin_`、読み取りキーの接頭辞 `fcms_read_`。サーバ側には SHA-256 ハッシュのみ保存。
- 一覧の `limit` 初期値 10・最大 100。
- 公開読み出しのキャッシュヘッダは `Cache-Control: public, max-age=60`。メディアは `public, max-age=31536000, immutable`。
- 削除系はすべてゴミ箱へ移す。完全削除・ゴミ箱を空にする・reset・置き換え import は `confirm: <サイト名>` 必須。サイト名 = Worker の `SITE_NAME` 変数。
- 最後の有効な管理キーは revoke できない。
- エラー応答の形は `{ "error": { "code", "message", "issues"?, "hint"? } }`。`issues` の要素は `{ path, message, expected?, received? }`。
- ライセンス MIT。
- テストは `npm test`（ルート）で worker と CLI の両方が走ること。

### 本計画で確定させた判断（spec に無い、または spec が実装者に委ねた点）

- **ID 形式**: `<接頭辞>_<12文字の [0-9a-z]>`。エントリ `e_`、メディア `m_`、コレクション `c_`、キー `k_`。slug は `^[a-z0-9][a-z0-9-]{0,63}$`（アンダースコアを含まないので、id と slug は衝突しない）。取得時は id として探し、無ければ slug として探す。
- **コレクション名**: `^[a-z][a-z0-9-]{0,39}$`。予約語 `collections, media, trash, keys, export, import, reset, openapi.json` は使用不可。名前は作成後に変更不可。
- **フィールド名**: `^[a-zA-Z][a-zA-Z0-9_]{0,39}$`。
- **エントリの読み書き形**: 本文は `data` に入れ子で持つ（`{ id, slug, status, createdAt, updatedAt, publishedAt, data, html }`）。`html` は markdown フィールドだけを HTML にした `{ [field]: string }`。
- **`required` は公開時にだけ強制**する。型・maxLength などは下書きでも常に検証する（AI が少しずつ下書きを書けるように）。
- **画像・参照の書き込み**は id 文字列または `{ id }` を持つオブジェクトを受け付ける（読んだ値をそのまま書き戻せるように）。読み出しでは画像は `{ id, url, width, height, alt, mimeType }`、参照は id 文字列（`expand` 指定時はエントリ、ゴミ箱・不存在は `null`）。
- **既定の並び順**: `-publishedAt`（null は最後）→ `-createdAt`。
- **Markdown 内の生 HTML はエスケープ**する（プレビューや LP での XSS 防止）。
- **メディアの上限** 20MB。`width`/`height` は PNG/JPEG/GIF/WebP のヘッダから読み、他の形式は `null`。
- **プレビュートークン**: `base64url(entryId.expUnix).base64url(HMAC-SHA256)`、有効期限の既定は 24 時間。秘密鍵は `settings` テーブルに初回自動生成。
- **キャッシュ版番号**: `settings.content_version`（全体で1つ）。書き込み系の操作のたびに +1。
- **単一（single）コレクション**のエントリ公開は通常どおり `/api/:collection/:id/publish` で行う。
- **import の方式**: `mode: "merge"`（id で上書き追加）か `"replace"`（既存をすべてゴミ箱に移してから取り込む。confirm 必須）。エントリ・メディアの id は保持する。メディアは `url` があればサーバが取得し、無ければ同じ id のファイルが既に R2 にあることを要求する（CLI は先に `PUT /api/media/:id` で本体を送る）。
- **`GET /`** はサイトの自己紹介 JSON（`{ name: "femtocms", site, version, api, mcp, openapi }`）を返す。

## Review Focus

1. **日本語やスペースを含むファイル名**の画像を上げたとき、URL がパーセントエンコードされ、その URL で実際に取得できること（Task 7 にテストあり）。
2. **スキーマに無いフィールド名や SQL 断片**を `filter` / `sort` に渡されたとき、SQL エラーや 500 ではなく、使えるフィールド一覧つきの 400 を返すこと（Task 5）。
3. **スキーマ変更後の古いデータ**（例: 数値で保存された値のフィールドが markdown 型として作り直された）を読んでも 500 にならず、値をそのまま返し `html` は出さないこと（Task 6）。
4. **タイトルに `<script>` などを含む記事**を embed.js やプレビューで表示しても、HTML として実行されず文字として出ること（Task 11, 16）。
5. **同じ slug での同時作成**や、ゴミ箱にある記事の slug の再利用で、500 ではなく 409 と分かりやすい hint が返ること（Task 4, 8）。

    - `listCollections(ctx): Promise<Collection[]>`（ゴミ箱を除く）
    - `getCollection(ctx, name: string): Promise<Collection>`（無い・ゴミ箱は `not_found`）
    - `createCollection(ctx, input: unknown): Promise<Collection>`（同名がゴミ箱含めて存在すれば `conflict`。ゴミ箱にある場合の hint は「restore_from_trash で戻すか、ゴミ箱を空にしてから作成」）
    - `updateCollection(ctx, name: string, patch: unknown): Promise<Collection>`（name 変更不可。`kind` を single にするとき有効なエントリが2件以上なら `conflict`。`reference.collection` が存在しないコレクションを指していれば `validation_failed`）
    - 内部用 `getCollectionRow(ctx, name, opts?: { includeTrashed?: boolean })` は他の core モジュールが使ってよい。

### Task 3: エントリ data の検証と正規化（純関数）

**Files:**
- Create: `worker/src/core/validate.ts`, `worker/test/validate.test.ts`

**Interfaces:**
- Consumes: `FieldDef`, `Issue`（Task 2）
- Produces:
  - `interface ValidateResult { data: Record<string, unknown>; issues: Issue[]; refs: { media: string[]; entries: { collection: string; id: string }[] } }`
  - `validateData(fields: FieldDef[], input: unknown, opts: { enforceRequired: boolean }): ValidateResult`
    - `input` がオブジェクトでなければ issue `{ path: "data", message: "object required" }`
    - スキーマに無いキーは issue（message に「unknown field」、expected に使えるフィールド名の一覧）
    - `default` は値が `undefined` のときに入れる
    - image/reference は id 文字列か `{ id }` を受け、id 文字列に正規化する。存在確認はしない（refs に集めて呼び出し側が確認する）
    - `datetime` は ISO 8601 として `Date.parse` できる文字列。保存は `toISOString()` に正規化する
    - `list` は配列。各要素を子 fields で再帰的に検証し、path は `data.faq[2].question`
    - 各 issue の `expected` は人が読める型説明（例 `"string (max 100 chars)"`, `"one of: info, event"`, `"media id (m_...)"`）
